# F3.1 live implementation

## Binding

| Control | Live binding |
| --- | --- |
| Durable system of record | `timbrydges/timscodefactory` |
| Control-plane visibility | Public; application and product repositories remain separate and may stay private |
| Default branch | `main` |
| Main ruleset | `factory-main-protected` |
| Production control | GitHub Environment `production`, no owner approval step, and deployment branch restricted to `main` |
| Production source | Custom deployment branch policy matching only `main` |
| Runtime state | AWS DynamoDB table output as `FACTORY_STATE_TABLE` |
| Release identity | GitHub Actions OIDC subject `repo:timbrydges@214414801/timscodefactory@1345656137:environment:production` |
| Release storage | Versioned, private S3 bucket output as `FACTORY_RELEASE_BUCKET` |
| Ultimate Factory authority | Tim Brydges; unilateral approval, bypass, intervention, pause, stop, resume, and override |

The registry starts in `PAUSED`. Automated promotion to `PILOT` requires all required static and live preflight cases to pass. Tim may explicitly override that gate as the sole human Factory Owner; no outside approval is required for his changes. The control-plane repository is intentionally public so GitHub can enforce its ruleset and protected-environment gates without Enterprise Cloud; secrets, runtime state, customer data, and proprietary application code are prohibited here. The environment uses an explicit `main` deployment-branch policy because GitHub's "protected branches only" environment option does not treat a repository ruleset as a classic branch-protection rule.

The environment deliberately has no required reviewer. Tim can dispatch his own release or rollback without approving himself. Agent/controller releases are separately fail-closed in the workflow: they require an active release lease and Tim's persisted, commit-specific `AUTHORIZE_RELEASE:<source-commit>` owner event. The immutable OIDC default is configured through the repository Actions OIDC API and PF-21 verifies the exact emitted subject prefix.

## Permission enforcement

Repository path permissions are enforced in three layers:

1. The role contract limits each role's declared tools, GitHub permissions, writable paths, network, and secret handling.
2. `scripts/validate_registry.py` rejects unknown roles, missing profiles, reviewer write access, protected-path reachability, controller bypass, identity collision, provider-family collision, and OIDC subject drift.
3. GitHub's `factory-main-protected` ruleset requires a pull request, one code-owner approval, approval after the last push, resolved review threads, linear history, and both required checks for agents and collaborators. Tim's verified GitHub user is the sole always-on bypass actor.

GitHub itself cannot grant path-scoped contents tokens. Each automated writer therefore receives a separate credential profile and its output is admitted only through a pull request whose diff is checked against its role contract. A GitHub App installation token is the intended runtime credential; agents never receive Tim's human credential or owner bypass.

## Runtime-state boundary

GitHub stores contracts, work products, reviews, evidence indexes, and release definitions. DynamoDB stores only task state, leases, retries, budgets, timers, escalation data, deployment records, and append-only audit events.

Every automated authoritative mutation uses:

- controller workload identity;
- expected-version compare-and-swap;
- active, unexpired lease where authority is delegated;
- provenance-bound evidence;
- atomic state and audit persistence;
- default-deny transition rules.

An integrity failure transitions the Factory to `PAUSED`, revokes active leases, blocks dispatch, and requires owner resolution.

Tim may issue an audited owner override from any state to any state, approve his own change, dispatch without an agent lease, or stop the Factory immediately. Owner audit records provide traceability and never constitute an approval gate.

## AWS bootstrap

Run Terraform from `infra/aws` using an AWS administrator bootstrap identity. The stack creates:

- an encrypted, deletion-protected DynamoDB table with point-in-time recovery and lease TTL;
- a private, encrypted, versioned release bucket;
- a repository-and-environment-bound GitHub OIDC role;
- a least-privilege controller state policy.

For the first deployment, run `scripts/aws-bootstrap-cloudshell.sh plan` from
AWS CloudShell. The bootstrap creates a dedicated private, encrypted, versioned
S3 Terraform-state bucket, enables native S3 state locking, detects and reuses an
existing GitHub OIDC provider, initializes Terraform, and saves a reviewed plan.
Run the same script with `apply` only after reviewing that plan. CloudShell uses
the signed-in AWS identity; the script never requests or stores long-lived AWS
keys.

Bind the four values from `github_repository_variables` as GitHub repository variables. No AWS access key or secret access key belongs in GitHub.

## Release sequence

1. A protected merge to `main` passes registry CI and preflight.
2. `build-attest` creates a deterministic archive containing only manifest-listed files plus the manifest itself, re-verifies the embedded file hashes, and produces the SHA-256 digest, GitHub provenance attestation, and retained build artifact.
3. Tim dispatches `release-oidc` with `OWNER_OVERRIDE` task and lease sentinels; this direct owner path has no approval step. A controller dispatch instead supplies an active `release_automation` lease plus Tim's commit-specific owner event.
4. The workflow binds the requested artifact to a successful `build-attest` push on `main`, verifies its checksum and GitHub provenance attestation, and then assumes AWS authority using the immutable repository/environment OIDC subject.
5. `INITIAL_RELEASE` is accepted only when no current pointer exists. Every later release names the current release commit, whose deployment record, S3 key, exact S3 `VersionId`, metadata, and object checksum are reverified before publication.
6. The workflow uploads the new object with an explicit SHA-256 checksum, captures and re-verifies the actual S3 `VersionId`, then atomically writes an immutable deployment record, append-only release event, and compare-and-swap `CURRENT` pointer in DynamoDB.

The separate, manual `rollback-oidc` workflow is owner-only and AI-independent. Tim supplies the expected current commit, a previously released target commit, and an audit reason. The workflow verifies the target deployment's exact stored S3 version and checksum, then atomically appends a rollback event and moves `CURRENT` only if the expected commit and object version are still current.

An invalid digest, absent attestation, OIDC mismatch, stale release pointer, missing or altered rollback object, duplicate deployment, expired agent lease, or non-owner rollback fails closed. If object upload succeeds but the DynamoDB transaction loses a race, that S3 version remains unreferenced and never becomes `CURRENT`. Tim bypasses approval gates; artifact-integrity and compare-and-swap checks still apply to everyone.
