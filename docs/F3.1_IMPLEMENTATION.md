# F3.1 live implementation

## Binding

| Control | Live binding |
| --- | --- |
| Durable system of record | `timbrydges/timscodefactory` |
| Control-plane visibility | Public; application and product repositories remain separate and may stay private |
| Default branch | `main` |
| Main ruleset | `factory-main-protected` |
| Production approval | GitHub Environment `production`, reviewer `timbrydges` |
| Runtime state | AWS DynamoDB table output as `FACTORY_STATE_TABLE` |
| Release identity | GitHub Actions OIDC subject `repo:timbrydges/timscodefactory:environment:production` |
| Release storage | Versioned, private S3 bucket output as `FACTORY_RELEASE_BUCKET` |
| Human production authority | Tim Brydges |

The registry starts in `PAUSED`. Changing it to `PILOT` requires all required static and live preflight cases to pass and a reviewed governance pull request. The control-plane repository is intentionally public so GitHub can enforce its ruleset and protected-environment approval gates without Enterprise Cloud; secrets, runtime state, customer data, and proprietary application code are prohibited here.

## Permission enforcement

Repository path permissions are enforced in three layers:

1. The role contract limits each role's declared tools, GitHub permissions, writable paths, network, and secret handling.
2. `scripts/validate_registry.py` rejects unknown roles, missing profiles, reviewer write access, protected-path reachability, controller bypass, identity collision, provider-family collision, and OIDC subject drift.
3. GitHub's `factory-main-protected` ruleset requires a pull request, one code-owner approval, approval after the last push, resolved review threads, linear history, and both required checks.

GitHub itself cannot grant path-scoped contents tokens. Each writer therefore receives a separate credential profile and its output is admitted only through a pull request whose diff is checked against its role contract. A GitHub App installation token is the intended runtime credential; agents never receive Tim's human credential.

## Runtime-state boundary

GitHub stores contracts, work products, reviews, evidence indexes, and release definitions. DynamoDB stores only task state, leases, retries, budgets, timers, escalation data, deployment records, and append-only audit events.

Every authoritative mutation uses:

- controller workload identity;
- expected-version compare-and-swap;
- active, unexpired lease where authority is delegated;
- provenance-bound evidence;
- atomic state and audit persistence;
- default-deny transition rules.

An integrity failure transitions the Factory to `PAUSED`, revokes active leases, blocks dispatch, and requires owner resolution.

## AWS bootstrap

Run Terraform from `infra/aws` using an AWS administrator bootstrap identity. The stack creates:

- an encrypted, deletion-protected DynamoDB table with point-in-time recovery and lease TTL;
- a private, encrypted, versioned release bucket;
- a repository-and-environment-bound GitHub OIDC role;
- a least-privilege controller state policy.

Bind the four values from `github_repository_variables` as GitHub repository variables. No AWS access key or secret access key belongs in GitHub.

## Release sequence

1. A protected merge to `main` passes registry CI and preflight.
2. `build-attest` creates the control-plane archive, SHA-256 digest, GitHub provenance attestation, and retained build artifact.
3. The independently identified Factory Controller dispatches `release-oidc` with the successful build run, exact source commit, and prior S3 object version for rollback. Tim does not dispatch the workflow.
4. Tim approves the protected GitHub Environment deployment. Preventing self-review remains enabled because the controller, not Tim, initiated the run; approval binds the OIDC `sub` claim to `production`.
5. The workflow verifies source, manifest, registry, action pins, digest, and attestation before assuming AWS authority.
6. AWS accepts only the exact repository/environment subject, stores the versioned release, and conditionally creates a deployment record.

Any missing approval, invalid digest, absent attestation, OIDC mismatch, duplicate deployment, or missing rollback version fails closed.
